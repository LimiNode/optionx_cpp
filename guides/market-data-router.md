# Market Data Router Guide

Language: **English** | [Russian](market-data-router.ru.md)

This is the canonical guide for `MarketDataRouter`, provider registration,
subscription-scoped delivery, status replay, and bot-thread integration. The
Russian translation must be updated in the same pull request whenever this
contract changes.

## Purpose

`MarketDataRouter` connects public market-data subscriptions owned by a
`BaseMarketDataProvider` to concrete `IMarketDataSubscriber` objects. It solves
three related problems:

- a subscriber receives only the ticks, bars, and statuses for its own routes;
- each delivery carries the concrete provider subscription descriptor;
- application code can select providers by stable numeric IDs or string aliases
  instead of storing concrete provider pointers in bots.

Use `MarketDataRouter` when the application needs subscription ownership and
per-subscription delivery. Use `MarketDataHub` for fan-out of an already
available stream when the hub must not create or own provider subscriptions.
Both objects use the provider's three live callback slots, so they must not be
bound to the same provider at the same time.

The public include point is:

```cpp
#include <optionx_cpp/market_data.hpp>

namespace md = optionx::market_data;
```

The maintained runnable examples are:

- `examples/market_data_router_example.cpp` for explicit Router handles;
- `examples/market_data_subscriber_base_example.cpp` for a self-subscribing bot
  and cross-thread owner-loop dispatch.

## Object Model

| Type | Owner and meaning | Stability |
|---|---|---|
| `BaseMarketDataProvider` | Physical source that implements subscribe, unsubscribe, and live callbacks | One object lifetime |
| `ProviderInstanceId` | Runtime identity generated by each provider object | Runtime only |
| `MarketDataProviderId` | Non-zero provider key assigned by the application | Stable if application configuration keeps it stable |
| Provider alias | Exact, case-sensitive string mapped to `MarketDataProviderId` | Stable if application configuration keeps it stable |
| `SubscriptionId` | Physical subscription ID assigned by a provider | Provider-defined |
| `RoutedSubscriptionId` | Logical route ID assigned by one Router | One Router lifetime |
| `MarketDataSubscriptionHandle` | Concrete provider descriptor carried by batches and statuses | Valid after provider acceptance |
| `MarketDataRouterSubscription` | Move-only RAII owner of one pending or active route | Until moved, reset, unsubscribed, or Router shutdown |

Do not use one identifier in place of another. In particular:

- `MarketDataProviderId` is suitable for bot configuration; `ProviderInstanceId`
  is suitable for correlating objects during the current process;
- `RoutedSubscriptionId` identifies Router-owned lifetime state;
- `MarketDataSubscriptionHandle` identifies the provider subscription visible in
  market-data events.

Default-constructed strong Router IDs are invalid. Check `valid()` or use their
explicit boolean conversion; no public invalid-sentinel constant is required.

## Provider Registration

Registration is optional. Direct provider-reference overloads remain available,
but registered IDs and aliases decouple subscribers from application wiring:

```cpp
md::MarketDataRouter router;
md::MarketDataProviderId intrade_id{1001};

const bool registered = router.register_provider(
    intrade_id,
    intrade_platform,
    {"intrade", "primary-options"});
```

Registration has the following contract:

- Router stores a non-owning provider pointer. The provider must outlive its
  registration, every pending provider operation, and Router shutdown.
- The numeric ID, provider instance, and every alias must be unique inside one
  Router. Empty aliases and zero IDs are rejected.
- Aliases are exact and case-sensitive. `"Intrade"` and `"intrade"` are
  different keys.
- Registration does not open a websocket and does not claim callback slots.
  Binding is lazy when the first route for that provider is created.
- `unregister_provider()` succeeds only while the registration has no pending or
  active routes.
- `registered_provider_id(runtime_id)` maps an event's runtime provider identity
  back to the stable application ID while the registration exists.

Provider selection changes only how Router finds the provider. These calls use
the same routing implementation:

```cpp
auto direct = router.subscribe_ticks(provider, bot, request);
auto by_id = router.subscribe_ticks(intrade_id, bot, request);
auto by_alias = router.subscribe_ticks("intrade", bot, request);
```

A route created through a direct provider reference has an invalid
`registered_provider_id()`, because no stable registration was selected.

## Explicit Subscriber API

A receiver implements only the channels it needs:

```cpp
class Chart final : public optionx::market_data::IMarketDataSubscriber {
public:
    void on_tick_data(
            const optionx::market_data::TickDataBatch& batch) override {
        // batch.subscription identifies this concrete chart route.
    }

    void on_market_data_status(
            const optionx::market_data::MarketDataStatusUpdate& update) override {
        // update.subscription identifies the route affected by this status.
    }
};
```

Router stores subscribers as `weak_ptr`. The caller keeps the object alive:

```cpp
auto chart = std::make_shared<Chart>();

auto eur = router.subscribe_ticks(
    "intrade",
    chart,
    md::TickSubscriptionRequest(
        "EURUSD",
        md::MarketDataTransport::WEBSOCKET));

if (!eur.valid()) {
    // Router could not create a pending route.
} else if (eur.pending()) {
    // The route exists, but provider acceptance has not arrived yet.
} else if (eur.active()) {
    const auto provider_subscription = eur.provider_subscription();
}
```

`MarketDataRouterSubscription` owns route lifetime. Moving transfers ownership;
`unsubscribe()`, `reset()`, destruction, or Router shutdown releases it. Keep the
handle alive for as long as the stream is required.

The optional subscription callback reports desired-state acceptance by the
provider. It is not a transport-readiness callback:

```cpp
auto route = router.subscribe_ticks(
    intrade_id,
    chart,
    request,
    [](md::MarketDataSubscriptionResult result) {
        // SUBSCRIBED means the provider accepted the subscription.
        // READY arrives separately through on_market_data_status().
    });
```

## Self-Subscribing Bots

`MarketDataSubscriberBase` combines `IMarketDataSubscriber` with internal
storage for move-only Router handles. A derived bot can subscribe from its own
methods without exposing handles to the composition root:

```cpp
class TradingBot final : public md::MarketDataSubscriberBase {
public:
    TradingBot(md::MarketDataRouter& router, md::MarketDataProviderId provider_id)
        : MarketDataSubscriberBase(router),
          m_provider_id(provider_id) {}

    bool request_start() {
        return post_subscribe_ticks(
            m_provider_id,
            md::TickSubscriptionRequest(
                "EURUSD",
                md::MarketDataTransport::WEBSOCKET),
            [this](md::RoutedSubscriptionId route) {
                m_eur_route = route;
            });
    }

    bool request_stop() {
        return post_unsubscribe(m_eur_route);
    }

    void on_tick_data(const md::TickDataBatch& batch) override {
        // Runs in the configured owner loop when Router has a dispatcher.
    }

    void on_market_data_status(const md::MarketDataStatusUpdate& update) override {
        if (update.subscription.id == provider_subscription(m_eur_route).id) {
            // This status belongs to the EURUSD route.
        }
    }

private:
    md::MarketDataProviderId m_provider_id;
    md::RoutedSubscriptionId m_eur_route;
};
```

The derived object must already be owned by `std::shared_ptr` before any
subscribe helper is called. The base uses `enable_shared_from_this` to give
Router a weak subscriber reference. Do not add another `enable_shared_from_this`
base to the derived type.

Synchronous `subscribe_ticks()`, `subscribe_bars()`, `unsubscribe()`, and
`unsubscribe_all()` are for code already executing in the owner loop. The
`post_*()` variants are the cross-thread API described below.

## Delivery And Concrete Subscription Context

Provider batches and statuses may be either subscription-scoped or stream-level:

- if the provider supplies a valid `MarketDataSubscriptionHandle`, Router sends
  the event only to the corresponding active route;
- if the provider supplies an unscoped event, Router finds matching active routes
  and creates one delivery per route;
- before invoking the subscriber, Router writes that route's concrete provider
  handle into `batch.subscription` or `update.subscription`.

Therefore two subscriptions to the same symbol are still distinguishable by
provider subscription ID. Subscriber code should correlate events through
`subscription.provider_id` and `subscription.id`, not only through `symbol`.

Callbacks are collected under Router's mutex and invoked after the mutex is
released. Router does not call subscriber code while holding its container lock.

## Status Cache And Replay

Providers publish statuses as a stream-level lifecycle bus. Router adds
subscription context and provides late-route replay.

Consider this sequence:

1. An EURUSD route binds Router to a provider.
2. The provider publishes `BTCUSDT / TICKS / WEBSOCKET / READY`.
3. Router caches that stream status even if no BTCUSDT route exists yet.
4. A BTCUSDT route is created and accepted by the provider.
5. Router immediately delivers the cached status with the new BTCUSDT
   `MarketDataSubscriptionHandle` in `update.subscription`.

Replay follows these exact rules:

- Router caches the latest matching status, not only `READY`. A late route can
  receive the latest `CONNECTED`, `FAILED`, or `DISCONNECTED` state instead.
- The cache key is provider plus stream type, symbol, timeframe, and transport.
  `AUTO` and `HYBRID` transports participate as compatible selectors.
- Replay happens only after provider subscription acceptance, so the replayed
  update can carry that concrete subscription handle.
- Only statuses are cached. Tick and bar payloads are never replayed.
- The cache exists only while Router is bound to the provider. At least one route
  must keep that binding alive for Router to observe statuses that precede a new
  route. Removing the last route unbinds callbacks and discards the cache.
- Router replay is per route. Two logical subscriptions receive updates carrying
  their own concrete provider handles.

This is lifecycle replay, not historical market-data recovery. Historical
prefill and gap repair belong to `MarketDataContinuityService` and provider
history APIs.

## Owner Loop And Bot Threads

Without an owner dispatcher, Router preserves synchronous behavior. Subscribe,
unsubscribe, provider completion, and delivery must then already be serialized
by the application in one owner loop. A synchronous provider result and cached
status replay can run before `subscribe_*()` returns. Callback code should use
the concrete `subscription` carried by the event instead of assuming that the
caller has already stored the returned route in another field.

For dedicated or shared bot threads, construct Router with a thread-safe
dispatcher. `BaseTradingPlatform::post_task()` is the standard adapter:

```cpp
md::MarketDataRouter router(
    [&platform](md::MarketDataRouter::owner_task_t task) {
        return platform.post_task(std::move(task));
    });
```

The dispatcher contract is:

- it is safe to call from provider, websocket, and bot threads;
- accepted tasks are processed FIFO by one owner loop;
- it never executes a foreign caller's task inline;
- it remains available until subscriber cleanup and Router shutdown finish.

With a dispatcher configured, Router marshals provider subscription completions,
tick batches, bar batches, and status updates into that loop. Bots use:

- `post_subscribe_ticks()` and `post_subscribe_bars()`;
- `post_unsubscribe()` and `post_unsubscribe_all()`.

The returned `bool` means only that the owner loop accepted the command. It does
not mean that Router created a route, that the provider accepted it, or that the
transport is ready. Those stages are observed separately:

1. `post_*()` return value: command queue acceptance;
2. route callback: valid or invalid `RoutedSubscriptionId` after handle storage;
3. provider callback: typed subscribe/unsubscribe result;
4. `on_market_data_status()`: live stream readiness and lifecycle.

If the subscriber expires before a posted subscribe command runs, the command is
cancelled and its callbacks are not invoked. Once a configured dispatcher starts
rejecting work during shutdown, new provider completions and deliveries are
dropped rather than being invoked inline on the source thread. A route whose
completion was rejected remains pending until Router cleanup.

All Router callbacks are serialized by the owner loop, but fields read directly
from a different bot thread still require the bot's own mutex, atomics, or
message queue.

## Lifetime And Shutdown Order

The safe lifetime relation is:

```text
provider and owner dispatcher
    outlive Router
        outlives subscribers and posted cleanup work
```

Use this shutdown order:

1. Stop producing new commands from bot threads.
2. Request unsubscribe or destroy subscribers while the dispatcher still accepts
   work.
3. Keep processing the owner loop until unsubscribe commands and any nested
   provider completion callbacks are drained.
4. Call `router.shutdown()` from the owner loop. It is idempotent, releases
   provider callback slots, and requests unsubscribe for remaining active routes.
5. Stop the platform/dispatcher and then destroy providers.

Do not defer subscriber destruction until after the dispatcher is closed.
`MarketDataSubscriberBase` normally posts remaining handles as one cleanup task;
if posting is no longer possible, its destructor falls back to synchronous
release. That fallback prevents abandoned handles but is not a replacement for
correct owner-loop shutdown ordering.

## Common Failure Modes

- `register_provider()` returns false: check zero IDs, duplicate provider
  instances, duplicate IDs, empty aliases, and alias collisions.
- A route callback receives an invalid ID: check the provider key, request
  validity, subscriber shared ownership, Router shutdown state, and callback-slot
  conflicts.
- A route stays pending: the provider has not delivered its subscription result.
- `SUBSCRIBED` arrives but no prices do: inspect stream lifecycle statuses;
  acceptance and `READY` are separate states.
- A late route receives no replay: Router may not have been bound when the status
  occurred, or the type/symbol/timeframe/transport key may not match.
- A bot receives no callback after posting: continue pumping platform `process()`
  when using manual mode, and verify that the dispatcher accepted the command.
- Duplicate or cross-thread teardown behavior: drain subscriber cleanup before
  Router and platform shutdown.

## Related APIs

- `BaseMarketDataProvider`: physical subscription and live callback contract.
- `IMarketDataSubscriber`: minimal receiving interface.
- `MarketDataSubscriberBase`: self-subscription and handle ownership helper.
- `MarketDataHub`: non-owning stream fan-out alternative.
- `MarketDataContinuityService`: historical prefill and gap recovery boundary.
- `BaseTradingPlatform::post_task()`: platform owner-loop ingress.
